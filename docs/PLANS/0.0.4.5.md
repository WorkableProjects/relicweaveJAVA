# RelicWeave 0.0.4.5 — Stability and Compatibility Patch

**Target:** Minecraft Java Edition 1.20.1 · Minecraft Forge 47.3.0+
**Release type:** Patch / stability-focused follow-up to 0.0.4
**Status:** Proposed implementation plan for Claude Code
**Theme:** Consolidation, compatibility, and release-readiness

## Goals and scope

0.0.4.5 is not a new content expansion. It is a focused hardening pass that makes the 0.0.4 branch safe to ship and reduces risk for players, worlds, and future patches.

Primary goals:

- Fix the known issues that block a clean 0.0.4 release.
- Preserve every existing 0.0.2 item, recipe, enchantment, infusion, and player/world-data contract.
- Preserve the 0.0.3 source-item mapping contract exactly.
- Remove half-finished or inconsistent behavior before it becomes a compatibility problem.
- Improve reliability, test coverage, and clear status feedback without broadening scope.
- Keep all optional integrations soft and safe when Curios or other libraries are absent.

This plan is intentionally narrow. Anything that cannot be fully validated should be deferred, documented, or removed before shipping.

---

## 0. Non-negotiable implementation rules

1. Audit before editing.
   - Inspect current registries, data files, recipes, world-save handling, config, tests, and machine behavior before changing anything.
   - Do not assume IDs, tags, or balance values from design docs match the actual implementation.

2. Preserve existing compatibility.
   - 0.0.2 items, enchantments, infusions, recipes, ids, and saved data must continue to work.
   - The 0.0.3 source-item mapping matrix is a compatibility contract and must remain unchanged unless the maintainers explicitly revise it in a separate decision.
   - Iron Ingots and Nether Stars retain their existing mapped behavior unless directly approved.

3. Do not add hidden scope.
   - 0.0.4.5 is a patch-level release. Any large feature or untested addition belongs in a later milestone.
   - Avoid new dimensions, new boss rosters, or large new progression systems unless required to fix a release blocker.

4. Maintain optional integration safety.
   - Curios remains optional.
   - Missing optional dependencies must not prevent the mod from loading or rendering basic gameplay.
   - Server and dedicated-client testing must run with both Curios present and absent.

5. Server authority.
   - Recipe consumption, cooldowns, effects, hazard state, boss state, loot grants, and progression unlocks must be validated on the server.
   - Client-side prediction may exist for visuals only, not for game-state correctness.

6. Ship only what is testable.
   - If a mechanic cannot be validated in a realistic path, it should be disabled, simplified, or postponed.

## 1. Release focus: what 0.0.4.5 must fix

The goal of 0.0.4.5 is to close the highest-risk issues that would otherwise make 0.0.4 unreliable.

### Priority bug and stability areas

- Curios-based relic activation and item identification problems.
- One-sided or inconsistent enchantment/infusion mapping checks.
- Recipe and registry duplication or mismatched IDs.
- Boss, relic, cycle, and hazard state problems that cause progression softlocks or duplicate rewards.
- Missing or wrong machine completion feedback, status messaging, and server/client desyncs.
- Worldgen or dimension-entry issues that make The Vestige unsafe or unplayable.
- Null or invalid config values that crash or silently produce broken behaviors.

### Release risk categories

1. Front-door blockers
   - Mod fails to load.
   - Curios absent or present causes startup failures.
   - Custom dimension fails to register or players cannot enter/return safely.

2. Progression blockers
   - Required items or relics cannot be acquired or activated.
   - Key machines cannot process valid recipe inputs.
   - Tier, enchantment, or infusion progression is impossible or inconsistent.

3. Data integrity issues
   - Saved worlds or player data break on load.
   - One-time rewards trigger more than once.
   - Alchemical, relic, or crafting data resets unexpectedly across reconnects or restarts.

4. Quality and UX blockers
   - Missing tooltips or unreadable mechanic state.
   - No clear feedback for failures or blocked actions.
   - Ambiguous or buggy activation flow.

## 2. Compatibility contracts to preserve

These are explicit compatibility requirements that 0.0.4.5 must not violate.

### 2.1 Existing 0.0.2 compatibility

- Existing items, recipes, and registry IDs remain valid.
- Existing enchantments and infusions remain functional.
- Existing saved data remains valid unless a migration is precisely documented and tested.
- Existing Iron Ingot and Nether Star mapping behavior remains unchanged.

### 2.2 Planned 0.0.3 compatibility

The planned 0.0.3 matrix is protected and must remain intact:

| Source item | Transmutation Table output | Celestial Infuser output |
| --- | --- | --- |
| Prismarine Shard | Undertow | Tidal |
| Echo Shard | Resonance | Warding |
| Phantom Membrane | Steady Draw | Pursuit |
| Copper Ingot | Reprisal | Anchored |
| Ghast Tear | Soulguard | Warding |
| Oak Sapling | Reaping | Anchored |

This table is not optional, not negotiable, and not a staging target for later cleanup. It must remain consistent and automatically testable.

### 2.3 0.0.4 compatibility guardrails

- New 0.0.4 content must not overwrite or reinterpret 0.0.2/0.0.3 IDs.
- Registry, recipe, tag, and naming collisions must be checked before finalization.
- If a new behavior conflicts with the protected source matrix, the new content should be renamed or removed, not forced into the old mapping.

## 3. Required release workstreams

### 3.1 Audit and validation pass

Complete a repository audit before any 0.0.4.5 implementation, specifically covering:

- registry ids and namespaces
- recipe files and recipe IDs
- item tags and structure tags
- event handlers and capability data
- relic activation and Curios hooks
- machine code and completion state
- saved-data serialization and migration
- config default values and validation

Required result:

- a short audit document listing each high-risk area, the current state, and the fixed state expected for 0.0.4.5.

### 3.2 Curios and relic activation repair

This is a top-priority fix. The known issue is that some relics cannot be identified as activatable via the cycling relic key in Curios.

Fix requirements:

- Identify which relics fail activation detection and why.
- Ensure activatable relics are recognized consistently across inventory, hand slots, and Curios slots.
- Validate no duplicated or ghost relic entries are created by inventory movement or Curios state changes.
- Confirm cooldown, selection, and activation state are preserved when players move, drop, swap, die, respawn, reconnect, or change dimensions.
- Add validation tests covering a player with relics in multiple storage locations.

### 3.3 Recipe and mapping validation

0.0.4.5 should add robust validation for these invariants:

- every source item in the protected matrix has exactly one enchantment path and one infusion path
- no recipe silently produces a duplicate result or missing output
- machine completion feedback does not trigger on invalid or blocked recipe states
- recipe output, equipment restrictions, and item validation are consistent with the guidebook and JEI

Recommended implementation:

- centralize mapping validation in a single registry check or validation utility
- fail fast with a clear log message when a mapping is missing or duplicated
- add automated tests that fail if a protected source is one-sided or misconfigured

### 3.4 Machine reliability and feedback pass

Machine systems should do the following reliably:

- only emit completion feedback when a valid recipe completes
- never play completion sound or particles when inputs are invalid or transformation fails
- correctly handle output-full conditions and blocked recipes without consuming inputs incorrectly
- provide clear user-facing status text such as Missing ingredient, Output full, or Maximum infusions reached
- ensure server state remains authoritative for output, sound, and effects

### 3.5 Dimension and world safety pass

This includes any worldgen, gate, or dimension-entry issue that could cause softlocks or unsafe travel.

Focus on:

- safe spawn and arrival logic
- return travel reliability
- death/reconnect recovery
- no portal loops or invalid destination behavior
- no frame/structure misregistration
- chunk boundary and spawn safety rules

If a dimension feature cannot be proven safe, it should be disabled or simplified for 0.0.4.5.

## 4. Non-functional requirements for 0.0.4.5

### 4.1 Stability and performance

- No expensive dimension-wide scans on every tick.
- No runaway particles, block entities, or mob spawn loops.
- No repeated boss or reward grant on reconnect or restart.
- No large memory or object leaks from relic or dimension state.

### 4.2 Accessibility and clarity

- Status messages must be readable and explicit.
- Critical sounds must have a non-sound fallback like visible warning or subtitle.
- New or changed mechanics must surface their limits, cooldown, and valid use context in tooltip or guidebook text.

### 4.3 Mod compatibility

- Curios remains optional.
- No mandatory third-party dependency for basic gameplay.
- No server/client class reference leak into common code.
- Dedicated server startup must still work without client-only rendering dependencies.

## 5. Phased implementation plan for 0.0.4.5

### Phase 1 — Audit and lock the known breakages

- Review actual code for relic activation, Curios integration, and mapping validation.
- Confirm all 0.0.2 and 0.0.3 compatibility contracts in code.
- Record the exact known issues and the intended fix list.
- Confirm the current branch builds and passes existing tests before making changes.

Exit gate:

- audit complete
- known blockers enumerated
- baseline build is recorded

### Phase 2 — Fix the activation and data consistency bugs

- Repair Curios-based relic identification and activation detection.
- Verify inventory-to-Curios transitions do not reset cooldown or duplicate state.
- Fix any item or capability state that is accidentally duplicated or lost during movement.
- Confirm activation is server-authoritative and works for both present and absent Curios cases.

Exit gate:

- relic activation works correctly from valid locations
- cooldowns persist across movement, death, respawn, and disconnect
- no duplicate activation state remains

### Phase 3 — Harden machine and recipe logic

- Validate 0.0.3 protected mapping matrix and existing 0.0.2 mappings.
- Add automated checks for one-sided recipe definitions.
- Fix recipe consumption and output-full logic.
- Ensure completion feedback only happens when appropriate.
- Update JEI or guidebook content only where it is actually incorrect or missing.

Exit gate:

- machine states are correct under normal and edge conditions
- mapping validation fails on invalid configurations
- no blocked or failed recipe produces a false success state

### Phase 4 — Stabilize world, dimension, and progression systems

- Fix any broken entry, return, or progression path.
- Verify boss or dimension-state rewards are idempotent.
- Ensure resets, disconnects, relogs, and restarts do not produce duplicate rewards or softlocks.
- Validate all relevant player/world data transitions.

Exit gate:

- entering and leaving The Vestige is stable
- no progression softlock from death, relog, or reconnect
- one-time achievements and rewards are safe

### Phase 5 — Documentation, test coverage, and release readiness

- Update changelog notes and plan details for 0.0.4.5.
- Add or tighten tests for relic activation, mapping integrity, and recipe safety.
- Run a full compatibility pass with Curios present and absent.
- Confirm the build is release-ready.

Exit gate:

- patch is validated
- no known high-risk compatibility bug remains unresolved
- release notes reflect the actual state of the patch

## 6. Acceptance tests for 0.0.4.5

The patch is complete only when all of the following pass.

### Compatibility and mapping

- [ ] Existing 0.0.2 items, recipes, enchantments, and infusions remain valid.
- [ ] The 0.0.3 mapping matrix remains intact and every source item still has both a Transmutation Table path and a Celestial Infuser path.
- [ ] Iron Ingot and Nether Star mapping behavior is unchanged unless explicitly approved.
- [ ] No duplicate or missing registry IDs are introduced.
- [ ] Recipe validation fails when a protected source item is missing or miswired.

### Relics and Curios

- [ ] Relics that should be activatable are recognized as activatable in Curios and inventory contexts.
- [ ] Relic activation works correctly when Curios is present and absent.
- [ ] Cooldowns and active states persist through dropping, equipping, unequipping, death, respawn, disconnect, and reconnect.
- [ ] No duplicate effects or activation events occur from multiple copies or inventory locations.

### Machines and content flow

- [ ] Completion sounds, particles, and status messages trigger only on valid recipe completion.
- [ ] Failed or blocked recipes do not consume inputs or claim success.
- [ ] Output-full and invalid-entry states are reported clearly.
- [ ] JEI, tooltips, and guidebook text match actual behavior.

### Progression and world safety

- [ ] Dimension and portal entry/return behavior is reliable.
- [ ] No progression softlock occurs on death, relog, disconnect, or restart.
- [ ] One-time rewards are not granted multiple times.
- [ ] Existing worlds and player data remain safe after patching.

### Stability and compatibility

- [ ] The mod loads in single-player with Curios absent.
- [ ] The mod loads in single-player with Curios present.
- [ ] Dedicated server startup works without client-only optional dependencies.
- [ ] No runaway particles, mob spawn loops, or chunk-scanning issues appear.

## 7. Scope guardrails for 0.0.4.5

Do not include any of the following unless they are required to fix a direct release blocker:

- large new content expansions
- major new dimensions or biome systems
- large additional bosses
- broad balance overhauls
- nonessential relic redesigns
- optional-mod feature expansion beyond safety testing
- major refactors without explicit need and validation

This patch should be surgical, not aspirational.

---

## 8. Definition of done

0.0.4.5 is ready when:

- the known release blockers are fixed
- compatibility contracts are preserved
- Curios-related relic activation is stable and tested
- machine and recipe validation is reliable
- the patch does not add material new scope
- the build passes its validation and regression checks
- the changelog and version metadata match the actual release content

This patch should leave the project in a significantly safer state for a proper 0.0.4 or 0.0.5 follow-up without forcing another large, destabilizing rewrite.

---

## 9. Suggested Claude execution order

For Claude Code, the work should proceed in this order:

1. repo audit and exact issue list
2. Curios/relic activation fix
3. mapping validation and recipe safety checks
4. machine feedback and edge-case cleanup
5. progression/world safety verification
6. documentation and changelog updates
7. final build and compatibility validation

This order reduces the risk of patching the wrong systems before confirming the actual root causes.
